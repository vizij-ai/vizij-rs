A device's animations play through Arora's animation module, `@arora/animation` 3.0.0 (`arora-animation-module` 1), host-linked with the same module, function and parameter ids. `moduleAnimation(animation)` returns the module's format 2.0 `Clip`, which `load_clip` takes (and `reload_clip`), where it returned the `AnimationClip` `load_animation` takes. Each segment plays as its left keyframe's interpolation says: `linear`, `step`, or `cubic` as glTF's `CUBICSPLINE` Hermite on the keyframes' `inTangent` and `outTangent` (value units per second), the segment's chord slope where one is absent — so an untangented `cubic` plays the straight line its keys make, where it played an ease-in-out. The module plays numbers as `f64`; an animation writes each key in the type the store declares for it (`KeyMeta::ty`), so a Vizij's rig inputs keep holding `f32`. A key with no declared type takes `f32`, Vizij's number type, which keeps pages that read `.f32` working. What the module changes, as a page sees it: a player `play_at` holds before its time reports `waiting` with the state `playing`; a command takes effect at the device time of the last step, so the player states read right after it show it; a window no longer moves the playhead, and a player outside it plays toward it; travel past a bound carries on past the wrap or the turn; `set_loop` takes `bounce`. `describe()`'s keyframes carry `inTangent` and `outTangent` (`AnimationKeyframe`). `decodePlayerStates` reads `PlayerState` 1.3.0: a player's `ended`, `window`, `reversed` and `waiting`, an instance's `startOffset` and `rate`.
